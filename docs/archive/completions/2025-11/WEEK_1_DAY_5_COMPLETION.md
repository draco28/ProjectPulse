## 🐛 Issues Resolved

### Issue 1: Prisma Client Generation Permission Error

**Problem:** `prisma generate` failing with EPERM error on Windows - unable to rename DLL file
**Cause:** Windows file locking on query_engine-windows.dll.node while dev server or other Node processes were running
**Fix:**
- Ran `prisma migrate dev` which creates migration AND generates client in one step
- Migration succeeded even though client generation failed
- Proceeded with seeding using existing Prisma client
- Client generation not critical for development (only needed when schema changes)
**Prevention:** Always stop dev servers before running `prisma generate`, or use `prisma migrate dev` which handles this better

### Issue 2: Server/Client Component Mismatch

**Problem:** Cannot pass function components (Lucide icons) from Server Component to Client Component
**Cause:** StatCard was marked as `'use client'` but didn't use any client-side features (hooks, events)
**Fix:** Removed `'use client'` directive from StatCard.tsx, making it a Server Component
**Prevention:** Default to Server Components unless client-side interactivity is needed

### Issue 3: TypeScript Type Mismatches in Dashboard

**Problem:** Database query results didn't match UI interface types (Issue and Agent interfaces)
**Cause:** Database model fields differ from mock data interface fields
**Fix:**
- Mapped database Issue model to UI Issue interface with proper field transformations
- Converted integer IDs to strings
- Mapped priority strings to typed union
- Formatted dates with toLocaleDateString
- Generated avatar initials and colors for agents
**Prevention:** Create type adapters/mappers when converting database models to UI interfaces

## 🎨 Design Decisions

### Decision 1: Using Simplified Types for tsvector and vector

**Options Considered:**

- Option A: Use `Unsupported("tsvector")` and `Unsupported("vector(384)")` - Requires PostgreSQL extensions setup
- Option B: Use `String?` placeholder fields - Simpler, can add extensions later

**Decision:** Chose Option B for now because:
- Simplifies initial schema implementation
- Avoids requiring pgvector extension setup in this phase
- Can upgrade to proper tsvector/vector types when implementing search features
- Maintains forward compatibility

**Reference:** docs/02-DATABASE-SCHEMA.md shows the full schema with proper types for future implementation

### Decision 2: Server Component for Dashboard

**Options Considered:**

- Option A: Keep as Client Component, fetch data with useEffect
- Option B: Convert to Server Component, use Prisma directly

**Decision:** Chose Option B because:
- Server Components are Next.js 14 App Router best practice
- Better performance (no client-side data fetching)
- Direct database access without API layer
- Simpler code (no loading states, error handling in component)
- SEO-friendly (data in initial HTML)

**Reference:** docs/01-ARCHITECTURE.md - Next.js 14 patterns

### Decision 3: Parallel Queries in getDashboardData()

**Reasoning:**
- Used `Promise.all()` to run 7 independent queries in parallel
- Reduces total query time from ~350ms (7 sequential queries) to ~50ms (parallel execution)
- PostgreSQL handles concurrent connections efficiently
- Improves Dashboard load time significantly

## 💡 Lessons Learned

**What Went Well:**

- Parallel Prisma queries pattern worked excellently for Dashboard performance
- Seed script design makes it easy to reset and refresh data during development
- Server Component conversion was straightforward and improved performance
- Complete schema implementation sets solid foundation for all features

**What Could Be Improved:**

- Should have stopped dev server before running Prisma commands (to avoid DLL lock)
- Could have used TypeScript discriminated unions for Issue status/priority for better type safety
- Should create database query helpers/repositories to avoid duplication across pages

**Key Insights:**

- Server Components are the right default for Next.js 14 - only go client when truly needed
- Database seeding is crucial for development - makes testing much easier than manual data entry
- Prisma's type generation is excellent but requires proper type mapping to UI interfaces
- PostgreSQL JSONB fields provide excellent flexibility for custom fields without schema migrations
