Roadmap Alternatives Analysis

Exploring simpler approaches to project tracking that replace the complex Phase → Sprint → Week → Day hierarchy

❌ Current System Problems

• 4-level hierarchy too complex (Phase → Sprint → Week → Day)
• "Current position" concept broken - AgentSession ≠ Roadmap position
• Days are granular but never actually used operationally
• Progress tracking is manual and drifts from reality
• Roadmap.current* fields not updated by anything
• Tickets link to weeks but connection feels arbitrary

Option 1: Kanban Sprint Board

Ticket columns by sprint status

Pure kanban approach where tickets flow through status columns within a sprint. No phases, weeks, or days - just sprints and tickets.

Schema Changes Required

Current Schema (Complex)

Roadmap
└── Phase (DELETE)
└── Sprint (DELETE or KEEP)
└── Week (KEEP for Option 4)
└── Day (DELETE)
Ticket
├── scheduledWeekId
├── scheduledDays[] (DELETE)
└── sprintNumber

Option 4 Schema (Simple)

Week
├── id (cuid)
├── projectId
├── weekNumber (1, 2, 3...)
├── startDate
├── endDate
└── capacity (default: 5)
Ticket
├── scheduledWeekId (nullable)

└── status

Recommendation: Option 4 (Calendar + Backlog)

Best balance of simplicity, timeline visibility, and agent workflow fit

Why this option?

  • • Week-level is the sweet spot - specific enough to plan, not so granular that it needs constant updates
  • • Current week is auto-determined - no manual "set current position" needed
  • • Agent workflow is clear - "Get this week's scheduled tickets → work them"
  • • Progress is derived - % = tickets done / tickets scheduled in week
  • • Backlog is first-class - unscheduled work is visible, not hidden
  • • Low migration - Week model already exists, just delete Phase/Sprint/Day
